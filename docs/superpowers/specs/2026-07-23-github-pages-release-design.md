# GitHub Pages 最简发布设计

## 背景

游戏已经是无需构建的静态页面，正式运行方式确定为 HTTP/静态托管，不再支持通过 `file://` 直接打开。当前仓库位于 GitHub，`main` 中的 `index.html` 与 `src/` 可以直接提供服务。

## 目标

- 使用 GitHub Pages 提供稳定的公网访问地址。
- 保持现有目录结构和零运行时依赖。
- 使用最少的发布配置和维护成本。
- 在发布前后完成与项目规模相称的可用性验证。

## 非目标

- 不新增 GitHub Actions workflow。
- 不引入 Playwright、打包器或其他发布依赖。
- 不增加发布分支、自定义域名、PWA 或离线能力。
- 不恢复双击 `index.html` 直接运行。

## 发布设计

GitHub Pages 直接使用 `main` 分支的仓库根目录作为发布源。游戏继续通过相对路径加载 `./src/game.js` 和 `./src/game-core.js`，无需生成构建产物。

发布流程如下：

1. 在本地 `main` 执行 `npm run check`。
2. 确认工作区干净后，将 `main` 推送到 `origin`。
3. 在 GitHub Pages 设置中选择 `Deploy from a branch`，发布源设为 `main / (root)`。
4. 等待 GitHub 生成正式地址。
5. 在正式地址完成一次人工可玩性验证。
6. 将正式地址和静态托管要求补充到 README，再提交并推送。

后续更新只需推送 `main`；GitHub Pages 使用其内置流程更新页面。

## 验收

发布前必须满足：

- `npm run check` 全部通过。
- `git status --short` 无未提交改动。

正式地址必须满足：

- 首页可以正常加载，没有资源 404。
- 点击或 Enter 可以开始游戏。
- 鼠标和键盘至少各完成一次有效移动。
- 游戏结束后可以重新开始。
- README 包含正式地址，并明确项目需要通过 HTTP 或静态托管运行。

## 失败处理

- Pages 未生成地址或返回 404 时，检查仓库 Pages 来源是否为 `main / (root)`，并查看 GitHub 内置部署状态。
- 页面出现资源 404 时，检查相对路径和文件名大小写。
- 发布版本不可用时，回退或修复 `main` 中对应提交后重新推送。
- 不为上述情况增加自定义发布脚本；当发布频率、协作者数量或失败成本明显增加时，再单独设计 CI/CD。
